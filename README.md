# Data Validation Toolkit

A config-driven validator that checks dashboard data for problems before it reaches users: missing fields, duplicates, broken links between tables, values that don't add up, and dates that don't make sense.

I built this around a scenario I've seen up close: a financial advisory dashboard pulls from several modules (clients, portfolios, meetings), and a single bad record can make a number on screen quietly wrong. Checking that by eye doesn't scale. This toolkit runs every rule automatically, explains what failed and the likely root cause, and gives a clear release recommendation.

> All data in this repo is synthetic and generated by `scripts/generate_sample_data.py`. Names, tickers, and values are made up.

## What it checks

Rules live in [`config/schemas.json`](config/schemas.json), so adding a check means editing config, not code.

| Check | Example it catches | Severity |
|---|---|---|
| Required fields | Client with a blank last name | Critical |
| Uniqueness | Same client ID entered twice | Critical |
| Data type | `2025-13-02` in a date field | Critical |
| Referential integrity | Holding linked to an account that doesn't exist | Critical |
| Calculated fields | Market value doesn't equal quantity x price | Critical |
| Cross-module reconciliation | Account total on the dashboard doesn't match the sum of its holdings | Critical |
| Allowed values | Risk profile typed as "Agressive" | Warning |
| Format (regex) | Email missing a domain | Warning |
| Min values | Negative share quantity | Warning |
| Date logic | Meeting dated before the client was onboarded | Warning |

## Results on the sample data

The generator plants 13 known errors across the three modules. The validator caught all of them (14 issues total, since one negative-quantity row fails two checks).


| Severity | Table | Record | Detail |

Every issue also gets a likely root cause (for example, "Summary total isn't refreshed when underlying records change") so whoever picks it up knows where to start.

## How to run

```bash
pip install -r requirements.txt

# Generate sample data (already included in data/)
python scripts/generate_sample_data.py

# Run validation
python -m validator.runner

# Exit with code 1 if anything Critical is found (useful as a CI gate)
python -m validator.runner --fail-on-critical

# Run unit tests
python -m pytest
```

## Project structure

```
data-validation-toolkit/
├── config/schemas.json        # all rules: columns, types, allowed values, FKs, business rules
├── data/                      # synthetic CSVs for clients, accounts, holdings, meetings
├── scripts/generate_sample_data.py
├── validator/
│   ├── checks.py              # one small function per check
│   └── runner.py              # loads config, runs checks, writes report
├── tests/test_checks.py       # unit tests for every check
└── outputs/
    ├── validation_report.md
    └── validation_issues.csv
```

## Design choices

- **Config over code.** Business rules change more often than validation logic, so rules sit in JSON where a non-engineer can read and update them.
- **Everything loads as text.** The validator decides what's valid, instead of pandas silently converting bad values to blanks.
- **Severity drives the decision.** Critical means a number users see is wrong. Warning means the data is usable but needs cleanup. Only Critical issues block a release.
